# tagdrift-bisect — version-axis performance archaeology with a noise-gated attribution gate

Upstream: https://github.com/pypa/packaging

`tagdrift-bisect` measures the same workload on **every release tag of a real
library**, then, only when a tag-to-tag step exceeds the machine's measured
noise floor, binary-searches the commits between the two tags and reverse-applies
the located commit to test causality.  Nothing about this repository optimises
any upstream; its product is a *measurement*: which release changed performance,
by how much, and whether that step is attributable to one commit or is diffuse.

The three subjects are `pypa/packaging` (BSD-2-Clause/Apache-2.0),
`pallets/click` (BSD-3-Clause) and `python-poetry/tomlkit` (MIT); 15 release
tags each, none of them vendored.  Measured on 2026-11-17, CPython 3.12.3.

## What was measured (all numbers from this run)

`SpecifierSet.contains(Version(...))` is what pip does on every candidate
release.  Across **15 packaging tags, 21.1 → 26.3**, on the same corpus of 95
real installed-distribution version strings (epoch/dev/post/local segments
included), the workload became **17.9x faster**:

| library / workload | scale (passes) | 21.1 (median) | 26.3 (median) | ratio |
|---|---|---|---|---|
| packaging / specifier-contains | 1 | 4.531 ms | 0.295 ms | **0.0651x** |
| packaging / specifier-contains | 10 | 44.357 ms | 2.799 ms | **0.0631x** |
| packaging / specifier-contains | 50 | 223.656 ms | 12.531 ms | **0.0560x** |

The other two subjects, same method (15 tags, 3 scales, 7 timed samples +
3 warmups per cell):

| library / workload | tags | first → last | ratio |
|---|---|---|---|
| tomlkit / parse real `pyproject.toml` | 0.11.8 → 0.15.2 | 453.874 ms → 295.895 ms (large) | 0.652x |
| click / 27-parameter CLI parse | 8.1.6 → 8.5.1 | 230.380 ms → 193.349 ms (large) | 0.839x |

## Tag-to-tag steps and single-commit attribution

Steps are flagged only when `|ratio-1| > max(3 × within-tag IQR, 2%)`; the
within-tag IQR is the measured spread of the 7 repeated samples of the *same*
tag, and an A/A control re-measures the first tag under a second label.

| step | endpoint ratio | bisect commit | subject | separation vs noise floor | revert |
|---|---|---|---|---|---|
| packaging 26.2 → 26.3 | **0.293x** | `40d76fb` | Implement Specifiers and SpecifierSets filtering using ranges (#1120) | **52.4%** vs 12.7% floor → attributable | not clean: later edits to `_ranges.py` conflict (reported, not hidden) |
| click 8.1.7 → 8.1.8 | **0.690x** | `70c673d` | Fix eagerness of help option generated by `help_option_names` (#2811) | **36.4%** vs 32.4% floor → attributable | code-only reverse-apply accepted: 0.0306 ms → 0.0470 ms vs 0.0443 ms baseline (**1.060x**, inside the 32.4% noise floor, outside the strict 2% gate) |
| packaging 25.0 → 26.0 | 0.357x | `39b0432` (best candidate) | perf: lazily calculate `_key` in `Version` (#989) | 8.8% vs 23.5% floor | **not** attributable — marked `diffuse` |
| click 8.3.3 → 8.4.0 | 1.015x | — | — | endpoint does not reproduce at `large` | **not** a regression (the tag-level flag was inside the 15.8% effective tolerance) |

The `diffuse` verdict is the point of the gate: the 2.8x step inside
25.0 → 26.0 is real, but no single commit moves the median by more than the
machine's own 23.5% noise floor there, so the tool refuses to name one.  The
"best candidate" commit is exactly the kind of plausible-looking answer that a
naive bisect would have published.

## Evidence and gates

* **Samples**: 1008 raw JSON lines in `benchmark/raw/*.jsonl`
  (3 libraries × 15 tags × 3 scales × 7 timed samples, plus one A/A control per
  library); reproduced by the three commands below.
* **A/A control** (first tag measured twice): packaging 1.027–1.094x,
  click 1.056–1.138x, tomlkit 0.944–1.099x — i.e. the machine's own error is
  disclosed, not subtracted away.
* **Semantic comparability**: every tag measured on the same workload produced
  the same sha256 output digest (`tests/test_diff.py::TestRealCorpusDigests`),
  so the timings compare code with identical behaviour.
* **Ground truth**: `tests/test_injected.py` builds a synthetic 12-commit repo
  whose commit 7 is a pure 6x timing regression; the bisect locates exactly
  that commit in <=9 measurements (<=4 binary-search probes + 5 fixed
  endpoint/control/verification runs) and the revert check returns to
  **1.0069x** of the baseline (strict +-2% gate passed on an idle machine; on a
  loaded machine the test asserts the noise-aware gate instead and still
  reports the strict number) (injected-regression certificate, not a claim about any upstream).
* **Differential**: `tests/test_diff.py` checks 1200 sha256-deduplicated
  distinct inputs give byte-identical output between the fast and slow
  implementations.

## Reproduce

```bash
git clone git@github.com:linluozi/tagdrift-bisect.git && cd tagdrift-bisect
git clone -q https://github.com/pypa/packaging /tmp/src_packaging   # or any ssh remote
python3 -m tagdrift.cli run --repo /tmp/src_packaging --workload packaging \
    --tags 21.1,21.2,21.3,22.0,23.0,23.1,23.2,24.0,24.1,24.2,25.0,26.0,26.1,26.2,26.3 \
    --out benchmark/raw/packaging.jsonl --reps 7 --warmup 3
python3 -m tagdrift.cli summarize --raw benchmark/raw/packaging.jsonl
python3 -m tagdrift.cli bisect --repo /tmp/src_packaging --workload packaging \
    --scale large --from-rev 26.2 --to-rev 26.3 --direction speedup --reps 9 --warmup 3
```

`python3 benchmark/run_real.py --src /tmp --reps 7 --warmup 3` reproduces the
whole 1008-sample study; `python3 -m tagdrift.cli selftest` reproduces the
injected-regression certificate; `python3 -m unittest discover -s tests -t .`
runs the 9-test suite (OK, 28.9 s on an idle machine).  The injected-regression
test is a *measurement*, so on a loaded machine its A/A control can exceed the
noise gate; it retries up to 3 times, and `TAGDRIFT_TEST_REPS=11` makes it
stricter.  No third-party dependency is required.

## Environment

AMD EPYC 7K62 ×4 vCPU, 3723 MB RAM, CPython 3.12.3 (only interpreter present;
3.10/3.11/PyPy are absent, so no cross-interpreter comparison is reported).
Timing uses `time.perf_counter()`; each cell is 3 warmups + 7 timed samples;
no seed is involved (the corpora are fixed files).  Every revision is measured
in a throwaway `git worktree` with `PYTHONDONTWRITEBYTECODE=1` and all
`__pycache__` removed, so byte-code caches cannot leak between tags.

## Scope note

This is a measurement tool, so there is no `patch.diff`: no upstream file is
modified, and nothing here is proposed for upstream review.  The measured
upstreams are checked out read-only into `/tmp` worktrees.

## 本轮创新

**新在哪**：把「同一库沿版本轴的性能轨迹」做成逐 tag 重放 + 噪声地板校准 +
单 commit 归因闸门，并第一次对 `packaging` 的 specifier 匹配给出跨 15 个 tag
的 17.9x 量化（26.2→26.3 的 3.4x 归因到 `40d76fb` / #1120，`parent↔culprit`
同树 A/B 分离度 52.4% > 12.7% 噪声地板）。

**和谁不一样**：台账里的 `perfdrift-ident` 只在单库上做区间不可辨识性证明、
`sametree/pr-evidence` 做已开 PR 的同树复核，都没有「先测整条版本轴、再用
A/A + within-tag IQR 定出噪声地板、只把超过地板的步做 bisect」这条闭环。

**凭什么推翻旧结论**：它推翻了两个本会被写进 README 的假结论——
(i) click `8.3.3→8.4.0` 在 tag 表里显示 +16%，但 `large` 尺度端点只有 1.015x，
判为噪声而非回归；(ii) packaging `25.0→26.0` 的 2.8x 步在逐 commit 复测后
不满足分离度闸门，判为 `diffuse`，不指名任何 commit。 换一个上游这套流程
仍然成立，但结论必须重新测（工具是通用的，结论不是）。
